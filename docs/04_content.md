## 1. `/learn/github` 内容

各セクションは「ひとことで言うと」「具体例」「何のためにあるか」「試してみよう」の4ブロック構成。

### セクション 1: GitHub って何？

- ひとことで言うと：チームでコードを共有・保存する場所
- 具体例：GitHub.com にプロジェクトを置くと、世界中からアクセス・コラボできる
- なぜ：1人で開発する場合も、後から「いつどう変えたか」が追える
- 試してみよう：GitHub アカウントを作って、自分用リポジトリを1つ作る

### セクション 2: リポジトリとは？

- ひとことで言うと：プロジェクトを置く場所
- 具体例：1 つの Web サイトに対して 1 つのリポジトリ
- なぜ：プロジェクト単位で履歴・Issue・PR を管理できる
- 試してみよう：空のリポジトリを作って README を1行書く

### セクション 3: Issue とは？

- ひとことで言うと：やることメモ
- 具体例：「トップページに自己紹介カードを追加する」
- なぜ：「誰が何をやるか」を見える化し、後から経緯を追える
- 試してみよう：自分のリポジトリで Issue を1つ立てる

### セクション 4: Branch とは？

- ひとことで言うと：作業用の分岐
- 具体例：`feature/profile-card` で作業して、完成したら main に取り込む
- なぜ：他人の作業に影響を与えずに自分の変更を進められる
- 試してみよう：`git switch -c feature/test` で新しいブランチを作る

### セクション 5: Pull Request とは？

- ひとことで言うと：変更を見てもらう提出箱
- 具体例：「この変更を main に取り込んでいいですか？」と提案する
- なぜ：レビューを受けてから本流に取り込むため
- 試してみよう：軽微な変更で PR を1つ出してみる

### セクション 6: Review とは？

- ひとことで言うと：変更内容の確認
- 具体例：「この変数名はもっと分かりやすくしては？」と指摘する
- なぜ：他人の目を通すことでバグや改善点が見つかる
- 試してみよう：他人の PR にコメントを付けてみる

### セクション 7: Merge とは？

- ひとことで言うと：本番の流れに合流させること
- 具体例：レビュー OK の PR を main に取り込む
- なぜ：レビュー済みの変更だけが本流に入る
- 試してみよう：自分の PR をマージしてみる

### セクション 8: Vercel Preview で確認するとは？

- ひとことで言うと：公開前にお試し画面で見ること
- 具体例：PR ごとに `*.vercel.app` の URL が発行される
- なぜ：本番に出す前にレビュアーが画面で確認できる
- 試してみよう：自分の PR でプレビュー URL を開く

### セクション 9: AI 開発ではどこで Claude Code / Codex / Antigravity を使う？

- ひとことで言うと：フローの各ステップで AI を差し込む
- 具体例：
  - Issue 起票 → そのまま Claude Code に実装依頼
  - PR 提出 → Codex が自動レビュー
  - レビュー後半 → Antigravity が画面確認
- なぜ：AI を「ツール」ではなく「フローの中の役割」として使うとブレない
- 詳細は `/workflow` へ

### 最後のミニ課題

```
お題: 「トップページに自己紹介カードを追加する」を最後まで通す

1. Issue を立てる
2. Branch を切る (feature/profile-card)
3. Claude Code に実装を依頼する
4. PR を作る
5. Codex にレビューしてもらう
6. Antigravity で画面を見てもらう
7. Vercel Preview で確認する
8. Merge する
```

→ 各ステップは `/workflow` のステップと完全対応。リンクで誘導。

## 2. `/workflow` の内容（中心ページ）

### 8 ステップ詳細

#### Step 1: Issue を立てる

- 何をするのか：これからやる作業を Issue として書く
- なぜ必要なのか：後から経緯を追える、チームに見える化される
- 初心者がハマりやすいところ：タイトルが曖昧になる、受け入れ基準が書かれない
- AI ツールをどう使うのか：ChatGPT 等で「この機能の Issue を書いて」と相談
- 自分で試すための小さな課題：自分のリポジトリで Issue を1つ起票

#### Step 2: Branch を切る

- 何：`feature/...` のようなブランチを作って作業を始める
- なぜ：main を壊さないため
- ハマり：ブランチ名が雑、main で直接作業してしまう
- AI：Claude Code に「`feature/profile-card` で作業を進めて」と伝えると認識する
- 課題：`git switch -c feature/test` を実行する

#### Step 3: Claude Code に実装を依頼する

- 何：Issue の内容を Claude Code に伝えて実装させる
- なぜ：実装の手数を減らし、レビューに集中できる
- ハマり：プロンプトが粗い、CLAUDE.md がないと文脈が薄い
- AI：Issue の内容をそのままコピーして渡すのが手堅い
- 課題：自分のリポジトリで Claude Code に「README に1行追加して」と依頼

#### Step 4: PR を作る

- 何：作業ブランチから main へ PR を作る
- なぜ：レビューを受けて本流に取り込むため
- ハマり：description が空、関連 Issue がリンクされない
- AI：PR テンプレに「Codex への指示」欄を入れる
- 課題：PR を1つ出して description にスクショを貼る

#### Step 5: Codex にレビューしてもらう

- 何：PR に対して Codex が自動でコメントを付ける
- なぜ：型エラー / 命名 / テスト漏れを人間レビュー前にフィルタ
- ハマり：的外れな指摘もある、全部対応しなくていい
- AI：PR テンプレに「設計の根拠」を書くと Codex の判断精度が上がる
- 課題：自分の PR で Codex の指摘を1つ取り込む

#### Step 6: Antigravity で画面確認する

- 何：完成画面を Antigravity（ブラウザ操作 AI）に見せて、不具合がないか確認
- なぜ：人間の目では見落とすレイアウト崩れを拾える
- ハマり：待ち時間の指示が必要、スクショ保存先を明示するとレビューしやすい
- AI：プレビュー URL を渡して「30 秒見て報告して」が王道
- 課題：自分のプレビュー URL を Antigravity に渡してみる

#### Step 7: Vercel Preview で確認する

- 何：PR ごとの Preview URL を実機で開く
- なぜ：本番反映前に画面で動作確認
- ハマり：環境変数の差異、ビルドエラーで Preview が出ない
- AI：Antigravity が URL を回遊できるので併用
- 課題：自分の PR の Preview URL をスマホでも開く

#### Step 8: Merge して公開する

- 何：レビュー OK の PR を main にマージ → Vercel が自動で本番デプロイ
- なぜ：レビュー済みの変更だけが本番に入る
- ハマり：Squash / Merge / Rebase の違いを理解せずに押す
- AI：マージ前後のスクショを Cases に残すと教材になる
- 課題：自分の PR をマージして本番 URL で確認

## 3. ツールページ詳細（7 本）

各ツールページは `03_pages.md` の共通テンプレに沿う。
中身の濃さは「使いどころ」中心に。

### 3.1 GitHub（🟢）

- ひとこと：Issue / Branch / PR / Review / Merge をまとめて管理する場所
- フローのどこで：Step 1, 2, 4, 7（ほぼ全てに登場）
- 試したこと：ハッカソンでチーム開発、PR テンプレ運用
- 効果：レビュー履歴が残るので教材として最強
- 微妙：通知が多い、設定が複雑
- 駆け出しが最初に試すなら：Issue を1つ立てる
- 関連：`/learn/github`、Case 1〜4

### 3.2 Claude Code（🟢）

- ひとこと：ターミナルで対話しながらコードを書ける AI
- フローのどこで：Step 3（実装担当）
- 試したこと：このサイトの実装、過去リポジトリの調査
- 効果：CLAUDE.md を整備すると数時間分の作業を任せられる
- 微妙：大きい変更は分割しないとブレる、破壊的操作は確認が必要
- 駆け出しが最初に試すなら：自分のリポジトリで `claude` を起動して「説明して」
- 関連：Case 1

### 3.3 Codex（🟢）

- ひとこと：PR 提出時に自動レビューを書いてくれる AI
- フローのどこで：Step 5（PR レビュー担当）
- 試したこと：PR の型エラー検出、命名指摘、テスト追加提案
- 効果：人間レビュー前のフィルタとして働く
- 微妙：的外れ指摘もある、設計レビューはできない
- 駆け出しが最初に試すなら：自分のリポジトリで PR を1つ出す
- 関連：Case 2

### 3.4 Copilot（🟢）

- ひとこと：エディタ内で次の数行を補完してくれる AI
- フローのどこで：Step 3 補助（コーディング中の補完）
- 試したこと：import 文補完、テストパターン展開、JSDoc 生成
- 効果：流れを止めない補完
- 微妙：古い API を提案することがある
- 駆け出しが最初に試すなら：VS Code で関数名だけ書いて Tab
- 関連：Case 1（Claude Code との併用）

### 3.5 Antigravity（🟡）

- ひとこと：ブラウザ操作を AI に任せられる
- フローのどこで：Step 6（画面確認）
- 試したこと：先週、Web アプリの画面巡回テスト
- 効果：レイアウト崩れを見つけられる
- 微妙：1 回しか使ってないので一般化はできない
- 駆け出しが最初に試すなら：プレビュー URL を渡して「30 秒見て」
- 関連：Case 3

### 3.6 Vercel（🟡）

- ひとこと：Next.js を簡単にデプロイできる
- フローのどこで：Step 7（Preview と本番デプロイ）
- 試したこと：web3-portfolio をデプロイ、PR プレビュー運用
- 効果：PR ごとのプレビュー URL でレビュー体験が変わる
- 微妙：ビルド設定でハマる、ログが見にくい
- 駆け出しが最初に試すなら：GitHub リポジトリを連携
- 関連：Case 4

### 3.7 他 AI（Gemini 等）（🔵）

- ひとこと：文章校正・要約・補助的な相談に使える AI
- フローのどこで：Step 1（Issue 起票時の相談）、Cases 執筆時の校正
- 試したこと：未使用、公式ドキュメントの整理のみ
- 効果：（公式ドキュメント参照）
- 微妙：著者は未使用、書ける範囲が限定的
- 駆け出しが最初に試すなら：Google AI Studio で無料お試し
- 関連：Case なし（試したら追加）


### 4.2 Case 1: Claude Code に UI 実装を任せた（🟢）

- やりたかったこと：トップページのヒーロー実装を Claude Code に任せる
- 使った AI / ツール：Claude Code、Vercel
- 投げた指示：「Next.js 16 + Tailwind v4 で、AI Dev Field Guide のヒーローを作って」
- 返ってきた結果：実装差分、スクショ、所要時間
- 良かった点：Tailwind v4 のクラス命名が正確、レスポンシブまで考慮されていた
- 微妙だった点：色味の調整は人間が必要
- 駆け出しへのアドバイス：CLAUDE.md でデザイン方針を伝えると一発で決まる

### 4.3 Case 2: Codex に PR レビューさせた（🟢）

- やりたかったこと：PR で Codex にレビューを任せて指摘を取り込む
- 使った AI / ツール：Codex、GitHub
- 投げた指示：（PR テンプレに「型と命名を中心に見て」）
- 返ってきた結果：型エラー N 件、命名提案 N 件
- 良かった点：人間レビュー前のフィルタとして優秀
- 微妙だった点：的外れな指摘もあった（具体例で示す）
- 駆け出しへのアドバイス：全部対応しないでよい、人間判断と併用

### 4.4 Case 3: Antigravity に画面確認させた（🟡）

- やりたかったこと：プレビュー URL の画面崩れを確認
- 使った AI / ツール：Antigravity、Vercel Preview
- 投げた指示：「このプレビュー URL を 30 秒見て、レイアウト崩れがないか報告して」
- 返ってきた結果：スクショ、気づきメモ
- 良かった点：人間が見落とすところを拾えた
- 微妙だった点：1 回しか試していないので過剰な一般化はできない
- 駆け出しへのアドバイス：プレビュー URL とセットで使うと体験が良い

### 4.5 Case 4: Vercel Preview で確認した（🟡）

- やりたかったこと：PR ごとに Preview URL を発行して動作確認
- 使った AI / ツール：Vercel
- 投げた指示：（GitHub 連携の設定だけ）
- 返ってきた結果：自動で URL 発行、PR にコメント
- 良かった点：レビュー時間が短くなる
- 微妙だった点：ビルドエラーで Preview が出ないとレビューが止まる
- 駆け出しへのアドバイス：環境変数を Production と Preview で分けておく
