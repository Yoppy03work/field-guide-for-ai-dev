## セクション 1: GitHub って何？

<Glossary term="GitHub" oneLine="チームでコードを共有・保存する場所" />

**具体例**

GitHub.com にプロジェクトを置くと、世界中からアクセス・コラボできる。

**何のためにあるか**

- 1人で開発する場合も、後から「いつどう変えたか」が追える
- チームで開発する場合は、メンバーで同じプロジェクトを進められる
- コードのバックアップ場所としても使える

**試してみよう**

- GitHub アカウントを作って、自分用リポジトリを1つ作る

</section>

<section id="section-2" className="scroll-mt-24">

## セクション 2: リポジトリとは？

<Glossary term="リポジトリ (Repository)" oneLine="プロジェクトを置く場所" />

**具体例**

1 つの Web サイトに対して 1 つのリポジトリ。
（例：このサイト `field-guide-for-ai-dev` も 1 つのリポジトリ）

**何のためにあるか**

- プロジェクト単位で履歴・Issue・PR を管理できる
- Public / Private でアクセス範囲を切り替えられる
- ファイル全体の変更履歴がたどれる

**試してみよう**

- 空のリポジトリを作って `README.md` を1行書く

</section>

<section id="section-3" className="scroll-mt-24">

## セクション 3: Issue とは？

<Glossary term="Issue" oneLine="やることメモ" />

**具体例**

「トップページに自己紹介カードを追加する」のような、これからやることを書く場所。
バグ報告にも使う。

**何のためにあるか**

- 「誰が何をやるか」を見える化する
- 後から「なぜこの変更をしたか」を追える
- 議論やフィードバックを 1 か所にまとめられる

**試してみよう**

- 自分のリポジトリで Issue を1つ立てる

</section>

<section id="section-4" className="scroll-mt-24">

## セクション 4: Branch とは？

<Glossary term="Branch (ブランチ)" oneLine="作業用の分岐" />

**具体例**

`feature/profile-card` で作業して、完成したら `main` に取り込む。

**何のためにあるか**

- 他人の作業に影響を与えずに自分の変更を進められる
- `main` は常に「動く状態」を保てる
- 並行で複数の機能を進められる

**試してみよう**

- `git switch -c feature/test` で新しいブランチを作る

</section>

<section id="section-5" className="scroll-mt-24">

## セクション 5: Pull Request とは？

<Glossary
  term="Pull Request (PR)"
  oneLine="変更を見てもらう提出箱"
/>

**具体例**

「この変更を `main` に取り込んでいいですか？」と提案する仕組み。
作業ブランチで完成した変更を、main にマージする前にレビューを受ける入口。

**何のためにあるか**

- レビューを受けてから本流に取り込むため
- 変更の意図と差分を 1 か所にまとめて議論できる
- マージ後も「なぜこの変更を入れたか」を後から追える

**試してみよう**

- 軽微な変更で PR を1つ出してみる

</section>

<section id="section-6" className="scroll-mt-24">

## セクション 6: Review とは？

<Glossary term="Review (レビュー)" oneLine="変更内容の確認" />

**具体例**

「この変数名はもっと分かりやすくしては？」と指摘する。
コメントで質問・提案を残し、Approve / Request changes でレビュアーが意思表示。

**何のためにあるか**

- 他人の目を通すことでバグや改善点が見つかる
- チームのコーディング規約・知識を共有できる
- 後から「なぜこの実装になったか」を読み返せる

**試してみよう**

- 他人の PR にコメントを付けてみる

</section>

<section id="section-7" className="scroll-mt-24">

## セクション 7: Merge とは？

<Glossary
  term="Merge (マージ)"
  oneLine="本番の流れに合流させること"
/>

**具体例**

レビュー OK の PR を `main` に取り込む。
`main` に入ると、そのコードが本番デプロイの対象になる。

**何のためにあるか**

- レビュー済みの変更だけが本流に入る
- 取り込みのタイミングと履歴がはっきり残る
- 後から `git log` で「いつ何が main に入ったか」が追える

**試してみよう**

- 自分の PR をマージしてみる

</section>

## セクション 8: Vercel Preview で確認するとは？

<Glossary
  term="Vercel Preview"
  oneLine="公開前にお試し画面で見ること"
/>

**具体例**

PR ごとに `*.vercel.app` の URL が自動で発行される。
レビュアーはその URL を開けば、実機の画面で動作を確認できる。

**何のためにあるか**

- 本番に出す前にレビュアーが画面で確認できる
- スマホ・PC など複数の環境で気軽に試せる
- 「コードだけ読んでも気づけない見た目の崩れ」を拾える

**試してみよう**

- 自分の PR でプレビュー URL を開いてみる

</section>

## セクション 9: AI 開発ではどこで Claude Code / Codex / Antigravity を使う？

<Glossary
  term="AI 開発フロー"
  oneLine="フローの各ステップで AI を差し込む"
/>

**具体例**

- Issue 起票 → そのまま **Claude Code** に実装依頼
- PR 提出 → **Codex** が自動レビュー
- レビュー後半 → **Antigravity** が画面確認

**何のためにあるか**

- AI を「ツール」ではなく「フローの中の役割」として使うとブレない
- どの場面でどのツールを使うかが明確になり、迷わない
- 後から「何を AI に任せ、何を人間が判断したか」が振り返れる

**詳しくは**

- [/workflow](/workflow) で 8 ステップの AI 差し込みポイントを見る
