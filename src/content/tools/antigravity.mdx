## ひとことで言うと

**ブラウザ操作を AI に任せられる**。
URL を渡すと、画面を巡回して気づいたことを報告してくれる。

<Callout type="warn" title="🟡 一部実体験">
  著者の Antigravity 体験は 1 件（別プロジェクトでの画面崩れ巡回）。
  ここで書く内容は「1 回試したらこうだった」レベル。
  過剰な一般化はせず、本サイト自身でも今後 PR ベースで試した記録を
  /cases に追記していきます。
</Callout>

## まずやること

[/tutorials/antigravity](/tutorials/antigravity) で 20 分のハンズオンが組んであります。
要点だけ：

1. 自分の Vercel Preview URL（または本番 URL）を 1 つ用意する
2. 観点を 3 つに絞った指示テンプレを書く（「致命 / 軽微」で要約させる）
3. Antigravity に投げて、報告を 1 件取り込む

## 開発フローのどこで使うか

- [Step 6: Antigravity で画面確認する](/workflow#step-6) … Vercel Preview と組み合わせて
- 「コードを読むだけでは気づけない見た目の崩れ」を拾うフィルタとして

## 実際に試したこと

- 別プロジェクトのプレビュー URL を渡して、モバイル幅でのレイアウト巡回（1 回）
- 観点を「横スクロール / 要素重なり / ファーストビュー文言」の 3 つに絞った

## 効果があったこと

- 人間が見落としやすいレイアウト崩れを拾える
- スクショと一緒に「ここが崩れている」と報告してもらえる
- Preview URL の再発行ごとに同じ観点で再確認させると、修正の効果が見える

## よくある失敗

- 指示が抽象的だと「特に問題なし」で終わりがち → 観点を 3 つ以内に絞り、Y/N で答えさせる
- 観点が多すぎると報告が散漫 → 「致命 / 軽微」で要約させるフォーマットを強制
- スクショ保存先が出力されない → 指示で保存先パスを明示
- 1 回限りの結果を「いつも効く」と過剰一般化 → 複数回試して初めて「自分の道具」になる

## 駆け出しが最初に試すなら

- まず [/tutorials/vercel](/tutorials/vercel) で Preview URL を用意する
- 自分のプレビュー URL を Antigravity に渡して「30 秒見て、レイアウト崩れがないか教えて」
- 報告内容を 1 件、PR で直して再確認させる（型ができる）
