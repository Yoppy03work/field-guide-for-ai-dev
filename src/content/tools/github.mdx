## ひとことで言うと

**Issue / Branch / Pull Request / Review / Merge をまとめて管理する場所**。
コードのバージョン管理（Git）に、チーム開発を進めるための入れ物が乗ったサービス。

## まずやること

「GitHub を使う」より「Issue → PR → Merge を 1 周する」が体に入りやすい。
[/tutorials/github](/tutorials/github) で 35 分のハンズオンが組んであります。

最短ルート：

1. アカウント作成 → 最初の repo
2. Issue を 1 つ立てる
3. Branch を切って編集 → PR を作る
4. Merge して Issue が自動 Close されるのを見る

ほぼ全てのステップに登場します。

## 実際に試したこと

- このサイト（field-guide-for-ai-dev）で 24+ PR を運用
- 過去のハッカソンでチーム開発（PR テンプレ運用）
- Issue → PR → Merge のサイクルを毎回回した

## 効果があったこと

- レビュー履歴が PR に残るので、後から「なぜこの実装になったか」を追える
- Issue / PR / Review のセットが教材として強力（自分用ログにもなる）
- `Closes #N` で Issue 管理コストがほぼゼロに
- main 基準のフローが、Vercel 自動デプロイと相性抜群

## よくある失敗

- main で直接作業してしまう → 編集前に必ず Branch を切る
- PR description が空 → 「何 / なぜ / 動作確認」の 3 行で十分
- Issue タイトルが曖昧（「修正」「アップデート」だけ） → 受け入れ基準を 3 件書く
- 1 PR に複数の独立変更を詰める → レビューが諦められる
- ブランチ命名が雑（`test`, `tmp`） → `<種類>/<issue#>-<説明>` の型を使う
